# Эпик: серверная корзина с API для веб- и мобильных клиентов

Статус: реализовано и проверено в ветке `codex/server-cart`.

## Цель

Перенести хранение и бизнес-логику корзины из веб-приложения Shoply на
бэкенд. Сервер отвечает за состав, допустимое количество, доступность товаров,
актуальные цены и итоговые суммы. Веб-приложение отображает полученные данные
и отправляет действия покупателя через API.

В этом эпике подключается существующая веб-витрина. API проектируется независимо
от Vue, маршрутов витрины и устройства покупателя, чтобы в будущем его могло
использовать мобильное приложение. Разработка мобильного приложения в эпик
не входит. Основа требований — согласованное обсуждение, отдельной исходной
спецификации нет.

## Текущее поведение

- [Cart store](../../frontend/src/stores/cart.ts) сохраняет состав в
  `localStorage` под ключом `shoply-basket`, изменяет количество и рассчитывает
  сумму по загруженному каталогу.
- [Действия корзины](../../frontend/src/composables/useCartActions.ts) изменяют
  локальное состояние и показывают уведомления.
- [Сервис заказов](../../backend/order_service.py) проверяет товары и рассчитывает
  цены при создании заказа. Отдельной серверной корзины пока нет.
- [Checkout store](../../frontend/src/stores/checkout.ts) сохраняет токен повтора
  оформления для защиты от дублирования заказа после сетевой ошибки.

## Требуемое поведение

- Корзина хранится на бэкенде и сохраняется после перезагрузки страницы
  и перезапуска сервера.
- При каждом чтении и изменении корзины сервер проверяет существование
  и доступность товаров, актуализирует цены и рассчитывает суммы.
- Любая успешная операция возвращает полный актуальный снимок корзины:
  позиции, цены, количества, суммы по позициям, общее количество, итоговую сумму,
  версию корзины и сведения о произошедших изменениях.
- Клиент не рассчитывает стоимость, не определяет доступность по локальному
  каталогу и не сохраняет состав как самостоятельный источник данных.
- На клиенте остаются отображение, форматирование, состояния загрузки,
  обработка ошибок и управление интерфейсом. В памяти можно держать последний
  ответ сервера для отображения.
- При сетевой ошибке клиент не показывает изменение как успешно выполненное.

Актуальность гарантируется на момент обработки запроса. Автоматическая доставка
изменений с сервера в уже открытый интерфейс в этот эпик не входит.

## Задача 1. Серверное хранение и идентификация корзины

Добавить хранение корзин и их позиций в SQLite. Для гостевого покупателя
предусмотреть безопасный идентификатор корзины, сохраняющийся между посещениями.

Отделить идентификацию клиента от предметных правил корзины: будущий мобильный
клиент должен использовать те же операции и правила. Обеспечить изоляцию корзин
разных покупателей и сохранить существующие проверки Origin/Host и защиту сессий.

Изменение схемы сохраняет существующие товары и заказы. Сервисы корзины
не зависят от FastAPI; HTTP-маршруты и схемы размещаются в существующих слоях
бэкенда. [Описание архитектуры](../../README.md).

Критерии готовности:

- Корзина восстанавливается после перезапуска приложения.
- Покупатель не может читать или изменять чужую корзину.
- Обновление существующей базы сохраняет товары и заказы.

## Задача 2. Отдельные операции API

Предлагаемый контракт для детализации перед реализацией:

| Операция | Запрос |
| --- | --- |
| Получить корзину, её состав и итоги | `GET /api/cart` |
| Добавить товар или увеличить его количество | `POST /api/cart/items` |
| Установить количество позиции | `PATCH /api/cart/items/{product_id}` |
| Удалить позицию целиком | `DELETE /api/cart/items/{product_id}` |
| Очистить корзину | `DELETE /api/cart/items` |

Уменьшение количества выполняется через изменение количества позиции.
Правила допустимых значений определяет сервер. Клиент передаёт идентификаторы
товаров и запрашиваемые количества; цены, суммы и доступность определяет сервер.

Описать схемы запросов, ответов и ошибок в OpenAPI. Предусмотреть безопасную
обработку повторных запросов и конкурентных изменений из нескольких вкладок,
включая защиту от применения устаревшего ответа. Повтор запроса после потери
ответа не должен непреднамеренно повторно увеличивать количество.

Критерии готовности:

- Все операции доступны через документированный API и возвращают актуальную корзину.
- Подмена клиентом цены или суммы не влияет на серверный результат.
- Повторные запросы и конкурентные действия не приводят к незаметной потере
  изменений или лишнему добавлению товара.

## Задача 3. Актуализация корзины

При чтении и изменении сервер:

1. Проверяет существование и активность товаров.
2. Исключает недоступные для заказа позиции.
3. Применяет текущие цены.
4. Проверяет количества по существующим ограничениям.
5. Пересчитывает суммы.
6. Возвращает изменения с устойчивыми кодами причин и данными для отображения.

В текущем Shoply доступность определяется существованием и активностью товара.
Учёт складских остатков и резервирование в эпик не входят.

Критерии готовности:

- Удалённый или скрытый товар исключается, итог пересчитывается,
  покупатель получает объяснение изменения.
- Новая цена отражается при следующем запросе корзины.
- Версия позволяет серверу определить, соответствует ли подтверждаемая корзина
  текущим данным. Чтение без изменений не создаёт ложный конфликт оформления.

## Задача 4. Проверка корзины при оформлении

Клиент передаёт версию корзины, показанную покупателю, и данные оформления.
Сервер повторно актуализирует корзину и проверяет, совпадает ли она
с подтверждаемой версией.

Если изменились состав, количество, цены или доступность:

1. Заказ не создаётся.
2. Сервер возвращает конфликт, актуальную корзину и перечень изменений.
3. Веб-приложение переводит покупателя на корзину либо оставляет её открытой,
   показывает обновлённые данные и объяснение.
4. Для создания заказа покупатель должен повторно подтвердить оформление.

Клиент не принимает изменения автоматически и не повторяет оформление
без действия покупателя. Если корзина к повторному подтверждению снова
изменилась, применяется тот же сценарий.

Если изменений нет, сервер создаёт заказ по серверной корзине. Проверка
и сохранение выполняются в одной транзакции, чтобы данные не изменились
между проверкой и записью заказа. После успешного создания оформленные позиции
удаляются из корзины. Повтор запроса не создаёт дополнительный заказ
и не очищает товары, добавленные позже.

Сохраняются статус «Ожидает оплаты», существующее поведение доставки
и защита от повторного создания заказа. Онлайн-оплата не подключается.

Критерии готовности:

- Изменение корзины между просмотром и оформлением блокирует создание заказа.
- Покупатель видит изменения и может оформить заказ после повторного подтверждения.
- Пустая после актуализации корзина не позволяет создать заказ.
- Успешный заказ содержит подтверждённые серверные цены и количества.
- Потеря ответа и повтор оформления не создают дубликат заказа.

## Задача 5. Подключение веб-приложения

Заменить локальную корзину в Pinia на состояние, полученное через API.
Перевести добавление, изменение количества, удаление и очистку на серверные
операции. API-сервисы не импортируют stores и не управляют интерфейсом.

Обновлять корзину при запуске витрины, открытии корзины, переходе к оформлению
и после операций с позициями. Показывать изменения после подтверждения сервера.

Сохранить существующий внешний вид, корзину поверх страницы, работу клавиатуры,
возврат фокуса, черновик формы оформления, обе темы и мобильную вёрстку.
При анимациях учитывать `prefers-reduced-motion`.

Критерии готовности:

- Изменения выполняются через API; локальные расчёты стоимости и сохранение
  состава в `localStorage` удалены.
- Уведомления об успехе соответствуют подтверждённому сервером результату.
- Ошибка загрузки отличается от пустой корзины; доступен повтор запроса.
- Устаревший ответ не заменяет более новое состояние корзины.
- Обновление корзины после конфликта сохраняет введённые данные оформления.

## Задача 6. Проверки и документация

Покрыть тестами изоляцию и сохранность корзин, все операции и ограничения
количества, удаление и скрытие товаров, изменение цен, конфликт оформления,
повторное подтверждение, конкурентные действия и сетевые ошибки.

Проверить отсутствие клиентских расчётов стоимости и сохранения состава,
создание заказа без дублирования и корректное очищение корзины.

При реализации выполнить:

```sh
python3 tests/test_shop.py
node tests/test_frontend.cjs
npm run typecheck
npm run lint
npm run format:check
npm run build
git diff --check
```

Проверить затронутые экраны в браузере на широком и мобильном размерах,
в обеих темах, включая клавиатурную навигацию. API-проверки и ручные сценарии
с записью должны использовать отдельную временную базу.

Обновить README и OpenAPI по фактическому поведению. Дополнительные проверки
выбирать по [инструкциям проекта](../../AGENTS.md), если реализация затронет
общие части приложения.

## Зависимости и решение о переходе

Сначала определить хранение, идентификацию и точный контракт API; затем
реализовать операции и актуализацию. Подключение веб-витрины и изменение
оформления опираются на этот контракт. Проверки сопровождают соответствующие
задачи; перед выпуском выполняется сквозная проверка.

Решение пользователя: существующие корзины из `localStorage` не переносить,
поскольку проект ещё не опубликован. Новая серверная корзина создаётся пустой.
Локальное сохранение состава и прежний модуль чтения корзины удаляются.

## Критерий завершения эпика

Веб-витрина использует серверную корзину как единственный источник
бизнес-данных. Покупатель получает актуальные данные при обращении к корзине
и не может оформить изменившуюся корзину без повторного подтверждения.
Будущий мобильный клиент может использовать тот же API без переноса правил
корзины в приложение.
