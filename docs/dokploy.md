# Деплой Shoply в Dokploy

Репозиторий подготовлен для одного экземпляра магазина на одном сервере. Сервер,
домен, HTTPS, GitHub App и секреты подключаются отдельно; добавление этих файлов
само по себе ничего не публикует. Локальная SQLite и загрузки в Git не отправляются.

## Настройка приложения на следующем этапе

1. Создайте Application в Dokploy и подключите GitHub с доступом только к нужному
   репозиторию. Выберите `mchikinov/Shoply`, ветку `main`, контекст сборки `/`,
   тип сборки Dockerfile, файл `Dockerfile` в корне.
2. **Отключите встроенный Auto Deploy Dokploy.** Иначе GitHub push запустит деплой
   независимо от тестов Actions. Не подключайте параллельный webhook GitHub.
3. Укажите переменные окружения из `.env.example`, заменив адрес сайта:
   `SHOPLY_PUBLIC_ORIGIN=https://ваш-домен`, `SHOPLY_HOST=0.0.0.0`,
   `SHOPLY_PORT=8765`, `SHOPLY_DATA_DIR=/app/var/data`.
   Схема и домен должны точно совпадать с адресом браузера. Используйте один
   основной домен, остальные перенаправляйте на него. Приложение не доверяет
   `X-Forwarded-Host` и `X-Forwarded-Proto`: прокси должен сохранять публичный Host.
4. До первого запуска задайте `SHOPLY_SETUP_TOKEN`: случайный секрет от 32 символов.
   Сгенерировать его можно командой `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`.
   Храните значение в менеджере паролей и настройках Dokploy; не коммитьте его.
5. Подключите **два постоянных именованных тома**:

   | Том (пример имени) | Путь контейнера |
   | --- | --- |
   | `shoply-data` | `/app/var/data` |
   | `shoply-uploads` | `/app/public/assets/uploads` |

   Контейнер работает от UID/GID `10001:10001`. Новые пустые Docker volumes
   наследуют права каталогов образа. Для существующих томов или bind mounts
   отдельно обеспечьте доступ этому UID; не открывайте права всем пользователям.
   Не монтируйте том поверх всего `/app` или `/app/public`: это скроет код сайта.
6. Оставьте одну реплику и стратегию обновления `stop-first`: сначала остановка
   старого экземпляра, затем запуск нового. Небольшой перерыв при деплое ожидаем.
   Сессии и лимиты попыток входа хранятся в памяти процесса; после обновления
   администратор входит повторно. Балансировка между несколькими репликами
   и запуск на нескольких узлах с локальной SQLite не поддерживаются.
7. В Domains настройте домен, HTTPS и внутренний порт `8765`. Не публикуйте этот
   порт непосредственно в интернет. Проверка готовности — `GET /api/health`,
   проверяющая HTTP и чтение базы. Образ содержит Docker HEALTHCHECK.
8. Выполните первый ручной Deploy. На компьютере с Python запустите
   `python3 scripts/setup_admin.py`, введите HTTPS-адрес, секрет, логин и пароль.
   Команда передаёт секрет заголовком; аргументы командной строки его не содержат.
   Затем войдите через `/admin.html`. После создания администратора удалите
   `SHOPLY_SETUP_TOKEN` из Dokploy и выполните повторный деплой.

Без секрета первый запуск с публичным адресом завершается ошибкой. Обычная форма
первоначальной настройки не обходит защиту. После создания администратора
повторная регистрация запрещена. Локальный запуск без новых переменных сохраняет
старый сценарий настройки через браузер.

## GitHub Actions после успешных проверок

Workflow `.github/workflows/checks.yml` проверяет API, витрину, админку, тему,
публичный режим и синтаксис JavaScript. Отдельная задача собирает Docker-образ,
создаёт тестовый заказ и загружает фото, удаляет контейнер, затем запускает новый
с теми же временными томами и проверяет сохранность данных и повторный вход.

Задача `deploy` зависит от обеих проверок и работает только на `push` в `main`.
Pull request не запускает публикацию. До подключения инфраструктуры она отключена.

В GitHub → Settings → Secrets and variables → Actions добавьте:

| Тип | Имя | Значение |
| --- | --- | --- |
| Variable | `DOKPLOY_URL` | HTTPS-адрес панели без пути и завершающего `/` |
| Variable | `DOKPLOY_APPLICATION_ID` | ID приложения из Dokploy |
| Secret | `DOKPLOY_API_KEY` | API-токен Dokploy с необходимыми правами деплоя |
| Variable | `DOKPLOY_DEPLOY_ENABLED` | `true`, только после первого успешного запуска |

Скрипт вызывает `POST /api/application.deploy`. Успех Actions означает, что Dokploy
**принял запрос**, а результат сборки и запуска нужно смотреть в Deployments.
Секрет и тело ответа не выводятся; перенаправления и автоматические повторы запрещены.

Перед запросом workflow сверяет проверенный commit с текущим `main` и пропускает
устаревшие запуски. Однако API запускает сборку настроенной ветки, а не фиксирует
проверенный commit: новый push между сверкой и загрузкой кода Dokploy может попасть
в эту сборку. На следующем этапе настройте защиту `main`: изменения через PR,
обязательные задачи `test` и `container`, запрет обхода проверок. Если нужна строгая
гарантия деплоя конкретного commit даже при параллельных push, потребуется отдельная
схема с публикацией и деплоем неизменяемого Docker-образа по digest.

Отключить следующие автоматические публикации можно переменной
`DOKPLOY_DEPLOY_ENABLED=false`. Это не останавливает уже начатую сборку в Dokploy.

## Данные и резервное копирование

На сервере сначала появятся демо-товары и новый администратор. Перенос локальных
товаров, заказов и фото — отдельная операция; Docker-образ их не содержит.

Для согласованной резервной копии остановите приложение и скопируйте оба тома:
SQLite и загруженные изображения. Храните копию вне этого сервера. Восстанавливайте
оба тома вместе и проверяйте восстановление. Не удаляйте тома при пересборке.
Откат кода не откатывает базу и не заменяет резервную копию.

Внешний HTTPS завершается в прокси Dokploy; внутри Docker-сети используется HTTP.
Публичный режим выставляет `Secure` для cookie и проверяет заданный Host/Origin.
Лимит попыток входа за прокси сейчас общий для его IP; IP из произвольных заголовков
не используется. Для публичной эксплуатации дополнительно настройте ограничения
размера/времени запросов и частоты обращений на прокси. Сервер стандартной библиотеки
остаётся простым сервером для небольшого магазина; большие нагрузки отдельно не проверены.
Онлайн-оплата по-прежнему не подключена.

## Проверки без публикации

```sh
python3 tests/test_deployment.py
# При установленном Docker:
docker build -t shoply-test .
SHOPLY_TEST_IMAGE=shoply-test python3 tests/test_deployment.py
```

Тесты используют временные данные и удаляют только свои контейнеры/фотографии.
Реальный домен, сертификат, доступ GitHub и вызов Dokploy проверяются после подключения.
